# Secrets across machines and projects: design (draft 2026-11-17)

Status: proposal, not implemented. Research notes are inline, and sources are at the end.
No secret values appear in this document. Names only.

## TL;DR

Four layers, each with one job:

| Layer | Holds | Delivered by | Who sees it |
|---|---|---|---|
| **sops-nix** (this repo) | Machine/system secrets and **bootstrap tokens** (Tailscale, Wi-Fi, syncthing, nix-serve, ntfy topic, *Bitwarden Secrets Manager machine tokens*) | `nixos-rebuild`; decrypted with **per-host** age keys | root / the owning service / the user if `owner = user` |
| **Bitwarden Secrets Manager** (`bws`) | **Project dev secrets** (API tokens, dev DB URLs, signing keys for dev), source of truth | `secretspec` with the `bws://` provider, token from sops | whoever holds a machine-account token. Scope = BWS project |
| **Bitwarden password manager** (`rbw`, browser extension) | **Personal** credentials and the *admin break-glass* copies (master age key, recovery codes, BWS org admin) | human only, on hazel (and butternut in desktop mode) | the human. Never unlocked on headless/agent hosts |
| **AWS IAM Identity Center** (+ instance role / Roles Anywhere) | Cloud credentials, short-lived | `aws sso login` (device code) / instance metadata | permission-set scoped: **Admin** (human) vs **Operator** (agents) |

**secretspec** (≥ 0.21, packaged from the nixpkgs that `llm-agents` already pins) is the
per-project *declaration + injection* layer: every repo commits a `secretspec.toml` that lists
**names** and points at one **alias** (`team`). Each machine's user config, generated by Nix,
says what `team` means on that machine (BWS project + token file). Same repo, same command
(`secretspec run -- …` or direnv `eval "$(secretspec export)"`) on every machine.

Two prerequisites matter more than the tooling. Without them, agents can read everything:
1. **Stop copying the single master age key to every host** (`scripts/install-host.sh` puts it in
   `~/.config/sops/age/keys.txt` on each machine, readable by the user, so readable by every
   agent, and it decrypts *every* host's secrets). Move to per-host keys derived from SSH host keys.
2. **Passwordless `doas` on agent hosts** gives agents root, so `/run/secrets/*` and everything else.
   Require a password (or `persist`) on hosts that run agents, or move agents to their own Unix user.
   See "Agent exposure model".

## Research findings

### secretspec

- **Version:** latest release **0.21.1 (2026-09-27)**. `main` has unreleased "0.22" items
  (`bw` session from another provider, SOPS delete). **nixos-26.05 ships 0.10.1. Too old**:
  no `bw`/`bws`/`sops`/`age`/`file` providers, no provider credentials, no `[defaults]` chain, no scopes.
  The nixpkgs revs already locked here via **`llm-agents`** (`nixpkgs_5`) and **`devenv`** both
  build **0.21.1** with all default features (`bw bws sops age awssm awsps vault keyring …`).
  So use `inputs.llm-agents.inputs.nixpkgs.legacyPackages.${system}.secretspec` with no new input.
- **Schema** (`secretspec.toml`, `revision = "1.0"`): `[project] name/revision/extends/require_reason`;
  `[providers]` aliases (`uri`, `credentials`, `cache`, `fallback`); `[defaults] providers = [...]` (0.21+);
  `[profiles.<name>]` with `KEY = { description, required, default, providers, ref, generate, composed, as_path, prompt }`;
  `[profiles.<name>.defaults]`; `[scopes.<name>] secrets = [...]` (0.17+).
  User config `~/.config/secretspec/config.toml` defines **user aliases** in `[defaults.providers]`.
  A project's `[defaults] providers = ["team"]` can name an alias that **only exists in user config**.
  This is the hook for "projects name needs, machines supply stores".
- **Providers now:** keyring, kdbx, dotenv, file, **bw** (official `bw` CLI, `BW_SESSION`), **bws**
  (official `bws` CLI, `access_token` credential or `BWS_ACCESS_TOKEN`), pass, gopass, 1Password,
  LastPass, Dashlane, Proton Pass, Passbolt, **awssm**, **awsps**, gcsm, akv/aac, Vault/OpenBao,
  Keeper, Infisical, Doppler, Tailscale **setec**, **sops**, **age**, ejson, env, **systemd-credential**,
  kubernetes, fly/cloudflare (write-only), null. **No rbw provider.** But 0.21 added **external providers**
  (`secretspec-provider-<scheme>` executables or `<scheme>.secretspec.json` claims, IPC "Secret Provider
  Protocol v1"), so an `rbw` bridge is possible later. It would need real code, not a shell one-liner.
- **Provider credentials:** an alias can load its own token from another provider
  (`credentials = { access_token = { provider = "file:///run/user/1000/secrets", ref = { item = "bws-token" } } }`).
  The credential is passed in memory to the provider and **not** exported to the child.
- **Cache:** an alias can have `cache = { provider = "<keyring|age|dotenv|pass…>", max_age = "8h" }`.
  This is useful on hazel offline (café), but the cache is plaintext-equivalent for agents if it's dotenv/age with a local key.
- **CLI:** `init`, `check`, `get`, `set`, `add`, `delete`, `import <provider>` (incl. `--delete-source`),
  `run [--profile] [--scope] -- cmd` (masks secret values in stdout/stderr), `export --format shell|dotenv|json|gha`,
  `config show`, `config global provider add`, `config provider login <alias>`, `cache clear`, `audit`,
  `serve` (SDK protocol), plus helpers `claude configure`, `docker configure`, `git configure`.
- **Agents:** `require_reason = "agents"` is the default. In a detected agent session (Claude Code etc., or
  `SECRETSPEC_AGENT=1`) access needs `--reason`, recorded in `secretspec audit`. This gives an audit trail,
  **not** an authorization boundary. Scopes are delivery-minimizing, also not a boundary (the docs say so).
- **devenv integration:** devenv CLI reads `secretspec:` in `devenv.yaml` and exposes
  `config.secretspec.secrets.*` to `devenv.nix`. **Not usable here:** routelab uses the flake-parts
  `devenv.flakeModule` via `use flake`, and putting secrets into Nix evaluation risks writing them
  into the world-readable store. Use direnv instead (below).
- **Headless:** `keyring://` needs a Secret Service on a D-Bus session with an unlocked collection
  (gnome-keyring is enabled only via the `email` feature, on butternut). On peacelily/maple/AWS VM
  and in lingering systemd user services there is none. **Don't use keyring for anything agents or
  headless hosts need.** Use `file://` (sops-rendered), `systemd-credential://`, `bws://`.

### Bitwarden

- `rbw` is a better daily CLI than `bw` (Rust, agent-cached, fast), but secretspec's `bw://` only
  speaks to the official `bw` CLI (Node, slow, separate login and `BW_SESSION`).
- **Bitwarden Secrets Manager** has a **free plan: 2 users, 3 projects, 3 machine accounts,
  unlimited secrets** (create a free organization next to the personal account). Machine accounts get
  **per-project read or read/write** access tokens. This is exactly the agent scoping we want.
  `bws` 2.0.0 is in nixos-26.05. secretspec shells out to `bws` and needs no SDK.
- rbw on a headless host: `pinentry-curses`/`pinentry-tty` works over SSH, but an unlocked
  rbw-agent exposes the **whole personal vault** to every process of the user. **Don't unlock rbw on agent hosts.**

### AWS

- **IAM Identity Center** gives short-lived role creds; the CLI refreshes role creds in the background
  while the access-portal session lives (default 8 h, configurable 15 min – 90 days, **global** setting).
  `aws sso login --use-device-code` works headless: run it on the target over SSH, open the URL on hazel/phone.
- **Caveat:** an *account instance* of Identity Center **cannot** grant AWS account access (no permission
  sets). You need an **organization instance**, which means AWS Organizations. If the TfC account
  is standalone and you are its admin, creating an Organization makes it the management account
  (acceptable at this size). If you are *not* the account owner, ask for Identity Center access, or use the fallback below.
- **Fallback without Identity Center:** `aws login` (CLI ≥ 2.32; nixos-26.05 has 2.34.24) turns a console
  sign-in (IAM user) into short-lived creds (auto-refresh every 15 min, hard cap 12 h; `--remote` for
  headless; profile key `login_session`). It needs the `SignInLocalDevelopmentAccess` policy on the IAM user.
  Alchemy supports it (`method: "console-login"`). Role assumption from it (`source_profile`) is unverified.
- **Unattended agents:** the AWS agent VM uses an **instance profile** with the operator policy (no secrets at all).
  Headless home hosts that must run *without* a daily human login could later use **IAM Roles Anywhere**
  (X.509 cert from a self-managed CA, deployed by sops, `credential_process` helper) mapped to the same
  Operator role. This is phase 2, optional.
- Alchemy (`~/.alchemy/profiles/*`) has methods `stored | sso | console-login`. Switch to `sso` with
  `ssoProfile = "tfc-admin"`.
- **ECR:** `amazon-ecr-credential-helper` (0.11.0 in 26.05) as a Docker `credHelpers` entry stores no tokens.

### DigitalOcean

- `doctl auth init --context <name>` stores tokens **in plaintext** in `config.yaml`. doctl also accepts
  `DIGITALOCEAN_ACCESS_TOKEN` / `--access-token`, so it can be injected by secretspec instead.
- DO personal access tokens support **custom scopes** and **expiry**. Create a read-only (or
  minimal) expiring token for agents, a separate one for humans, or **revoke** the current one if
  DO is no longer used (no repo references it now; the kube contexts are all EKS).

## Agent exposure model

Agents run as `hfahmi`, inside `agents.slice`, on butternut/peacelily/maple/AWS VM.
**Anything readable by the user is readable by agents.** Claude Code deny rules
(`Read(~/.config/sops/**)`, `Bash(doas:*)`) are speed bumps. `bash -c`, scripts, and other
agents (OpenCode) ignore them.

| Secret | Today | Target |
|---|---|---|
| master age key | on every host, user-readable | **hazel only** (or only in Bitwarden personal vault); hosts use SSH-host-derived age keys (root-only) |
| `/run/secrets/*` | root/owner, but doas is passwordless | doas needs a password on agent hosts. User-owned secrets limited to what agents may have (BWS agent token, ntfy topic) |
| personal vault | rbw unlocked up to 1 h on butternut/hazel | never unlocked on agent hosts. On butternut desktop mode use a short `lock_timeout` (e.g. 300) and the browser extension |
| AWS | static admin-ish keys everywhere | agents: **Operator** permission set via a *separate* Identity Center user (`…-agents`) so its SSO token can't be exchanged for Admin. Humans: Admin, only on hazel |
| project dev secrets | `.env` files, `gradle.properties` | BWS project per repo. **agents** machine account: read-only on `dev` projects. **human** machine account: read/write, hazel only |
| release keys (Android upload keystore, prod DB) | agent-readable files | not in any agent-readable store. Keep them in the personal vault/CI. Agents never sign releases |

**Why a separate Identity Center user for agents:** an SSO access token in `~/.aws/sso/cache` can be
exchanged for *any* permission set assigned to that user. If the human user has Admin and logs in on
a host where agents run, agents get Admin. With a dedicated agents user that has only Operator,
logging in on an agent host is safe by construction.

**Long-term (recommended for butternut, which is both desktop and agent host):** run `agent-host`
services (T3 Code server, herdr, `agent-run`) as a dedicated `agent` Unix user with its own
`~/.aws`, secretspec config and BWS token. That is the only real boundary against same-user agents.
Track it as a follow-up to the agentic workspace design.

## Split of responsibilities (who owns what)

- **sops (nixconf):** anything a *service* or *the machine* needs at boot, plus bootstrap tokens
  for the other layers (BWS machine tokens, Roles Anywhere cert/key later). Also non-secret-but-private
  config we don't want in a public repo (AWS start URL/account IDs, rendered via `sops.templates`).
- **Bitwarden personal vault:** human credentials and break-glass copies (master age key, BWS org
  owner, AWS root MFA recovery). Read by humans via rbw/browser.
- **Bitwarden Secrets Manager:** project dev secrets, the source of truth for what `secretspec` resolves.
  Three projects (the free limit): `routelab-dev`, `d_abm-dev`, `infra-dev` (nixconf/cachix/R2/ntfy/
  GitHub tokens for agents). Three machine accounts: `human` (rw all, hazel), `agents` (r on the three,
  agent hosts), one spare (`ci` or `aws-vm`).
- **secretspec:** declares names per project and injects at runtime. It never stores anything itself.
- **AWS Identity Center / instance roles:** all AWS access. No static keys anywhere (CI already uses OIDC).

## Per-project `secretspec.toml` drafts (names only)

Common pattern. The project names only the alias `team`, and machines define it:

```toml
#:schema https://secretspec.dev/schema/secretspec.schema.json
[project]
name = "routelab"            # BWS: project "routelab-dev"
revision = "1.0"
require_reason = "agents"     # default; makes agent access auditable

[defaults]
providers = ["team"]          # user-level alias, defined per machine by nixconf
```

## direnv integration (works with `use flake` + flake-parts devenv)

Add to each repo's `.envrc`, after `use flake`:

```bash
# secrets: names from secretspec.toml, values from the machine's `team` store
if has secretspec && [ -f secretspec.toml ]; then
  watch_file secretspec.toml
  eval "$(secretspec export --reason "direnv shell" 2>/dev/null)" \
    || log_error "secretspec: missing secrets (run: secretspec check)"
fi
```

Trade-off: this puts values into every shell and agent process started in the repo, which is
the same exposure as `.env` today but without files in worktrees. Stricter: don't export in `.envrc`.
Wrap only the commands that need secrets (`secretspec run --scope web -- pnpm dev`, Tilt, Lago)
in `package.json`/`justfile` scripts. Recommendation: **wrap commands** for routelab (many secrets),
**no secrets in env** for d_abm (only `AWS_PROFILE`).

## Nix modules to add (nixconf)

1. **`features/secretspec.nix`** (`flake.nixosModules.secretspec`, all hosts)
   - package: `inputs.llm-agents.inputs.nixpkgs.legacyPackages.${system}.secretspec` (0.21.1),
     plus `bws` (26.05), `pkgs.direnv` already present.
   - HM `xdg.configFile."secretspec/config.toml"`, generated from an option
     `preferences.secrets.teamToken` (path), e.g.:
     ```toml
     [defaults.providers]
     team = { uri = "bws://{project-uuid}", credentials = { access_token = { provider = "file:///run/user/1000/secrets", ref = { item = "bws-token" } } } }
     ```
     The BWS URI needs the *project UUID*, so define one alias per project (`team-routelab`,
     `team-d_abm`, `team-infra`) in user config, and in each repo use `[defaults] providers = ["team-<repo>"]`.
     Or keep UUIDs in the (private) repos' `[providers]` and only the token location in user config.
     **Verify** which works better with 0.21's alias/credential precedence.
   - `sops.secrets."bws-token"` with `owner = user`, `path = "/run/user/<uid>/secrets/bws-token"`,
     or HM sops (`sops-nix.homeManagerModules.sops`) to `$XDG_RUNTIME_DIR/secrets`. Choose the file per
     role: `secrets/shared/bws-agents.yaml` (agent hosts) or `secrets/hazel/bws-human.yaml` (hazel only).
     **Verify** the `file://` provider accepts sops-nix's symlinked layout (it rejects symlinks *inside* the root).
2. **`features/aws.nix`** (extend the existing module; drop `aws-vault` + `AWS_VAULT_BACKEND=file`, which nothing uses)
   - `sops.templates."aws-config"` (owner = user) rendering `~/.aws/config` with SSO start URL and
     account IDs from `secrets/shared/aws.yaml` (keeps them out of the public repo). HM
     `home.file.".aws/config".source = config.lib.file.mkOutOfStoreSymlink config.sops.templates."aws-config".path`.
     (Alternative if you accept account IDs in public: HM `programs.awscli.settings` directly.)
   - Profiles:
     ```ini
     [sso-session tfc]            sso_start_url = … ; sso_region = eu-central-1 ; sso_registration_scopes = sso:account:access
     [profile tfc-admin]          sso_session = tfc ; sso_account_id = … ; sso_role_name = AdministratorAccess ; region = eu-central-1
     [profile tfc-operator]       sso_session = tfc ; sso_account_id = … ; sso_role_name = CairoSimOperator ; region = eu-central-1
     [sso-session tfc-agents]     (same start URL; logged in as the agents Identity Center user)
     [profile tfc-agent]          sso_session = tfc-agents ; sso_role_name = CairoSimOperator ; …
     [profile tfc-vm]             credential_source = Ec2InstanceMetadata  # AWS agent VM only
     ```
   - `preferences.aws.defaultProfile`: `tfc-admin` on hazel, `tfc-agent` on agent hosts → `environment.variables.AWS_PROFILE`.
   - `amazon-ecr-credential-helper` + HM `~/.docker/config.json` `credHelpers` for the ECR registry.
3. **`features/rbw.nix`**: switch to HM `programs.rbw.settings` (`email`, `lock_timeout = 300`,
   `pinentry = pkgs.pinentry-qt` on desktops / `pinentry-curses` elsewhere). Import **only** on hazel
   and butternut, never in `agent-host`-only hosts. Add `Bash(rbw:*)`, `Read(~/.aws/sso/**)`,
   `Read(~/.alchemy/**)` to the managed Claude deny list in `agent-common` (speed bump, documented as such).
4. **sops per-host keys**: `sops.age.sshKeyPaths = ["/etc/ssh/ssh_host_ed25519_key"]`, drop `sops.age.keyFile`

## Risks and open questions

- **Same-user agents remain the root problem.** Everything here *reduces* blast radius (scoped BWS
  token, Operator-only AWS, no master key, no unlocked vault) but agents on a host can still read what
  that host's user can. Only a separate Unix user (or VM) is a boundary.
- **Identity Center needs Organizations.** If the TfC account isn't yours to reorganize, use plan B (`aws login`).
- **secretspec moves fast** (0.10 → 0.21 in ~5 months; "0.22" unreleased). Pin via the locked `llm-agents`
  nixpkgs and run `secretspec check` in CI. TOML features used here are all ≤ 0.21.
- **Bitwarden free tier limits** (3 projects / 3 machine accounts). Lago and android-release may need
  their own projects. Use profiles inside `routelab-dev` first, or pay for Teams ($6/user/mo).
- **bws/bw as subprocesses:** secretspec passes new values to `bws` on its command line when *writing*
  (visible in `ps` to the same user). Do writes from hazel only.
- **Offline (café, Egypt uplink):** BWS needs network. Add `cache = { provider = "age://…", max_age = "1d" }` on
  hazel only if this bites. That cache is a plaintext-equivalent copy for that user.
- **Exporting via direnv** leaks values into every child process and possibly into agent transcripts
  (`env`, error dumps). Prefer `secretspec run` wrappers (they also mask values in output).
- **Public repo:** keep start URL, account IDs and BWS project UUIDs out of nixconf (sops templates).
  The d_abm/routelab repos are private and already contain the account ID.
- To verify before implementation: `file://` provider with sops-nix paths; alias-per-project vs
  project-level `[providers]` with user-level credentials; `aws login` + `source_profile`; nixpkgs
  name of the Roles Anywhere signing helper; whether DO is still in use.
