## 0. TL;DR — the decisions

1. **Package:** llm-agents `t3code` (0.1.9 today; 0.1.10 shipped 2026-11-17 01:44 UTC), **`.override { providerPackages = []; }`**. By default the `t3` wrapper bundles codex, cursor-agent, grok, claude-code and opencode: a 2.6 GiB closure, about 2.2 GiB of it CLIs we don't want T3 to use [bin]. Hosts take the `out` output (server only, no Electron). hazel also takes the `desktop` output.
2. **Declarative control goes in `/etc/t3code/policy.json`** (T3's *managed policy*), generated by Nix and **checked at build time with `t3 policy check`**. Locked values can't be changed in the UI, and default values fill in whatever the user hasn't set [src][doc]. Keep `settings.json` and `keybindings.json` **mutable** (HM's merge mode). The server rewrites both files at runtime, and its atomic writer follows symlinks into the read-only store, so `mutable*=false` breaks writes [src].
3. **Exposure:** bind to loopback and add **`--tailscale-serve`**, which gives `https://<host>.<tailnet>.ts.net/` with a MagicDNS certificate. Don't use a plain `http://100.x:3773` bind. HTTPS is needed for app.t3.codes, for MCP sign-in from outside agents, for linked environments and for browser features that require a secure context (voice) [doc]. Tailscale Funnel: no. T3 Connect (`limits.connect=false`): off for now. You can turn it on later if you want phone push notifications.
4. **One client, many hosts:** the hazel desktop app with *Local environment* off, paired once with each host. A machine can have several routes (Tailscale HTTPS, LAN), and T3 picks the first one that answers [doc].
5. **Providers:** Claude (`claudeAgent`) plus OpenCode. Pin `binaryPath` to `/etc/profiles/per-user/hfahmi/bin/{claude,opencode}` in the policy: a stable path, so CLI bumps don't restart T3 [src]. Claude sessions use the Claude Agent SDK with the user's `~/.claude` (settings, hooks, skills, plugins) [src].
6. **Resources:** T3 already puts every agent and terminal in its own transient scope under `app-t3code-agents-<hash>.slice` (parent `app-t3code.slice`) [src]. **Agents therefore leave `agents.slice` by design.** Cap `app-t3code.slice` instead, and keep the server outside the cap, using T3's own unit properties.
7. **Projects:** register them declaratively with a user oneshot that runs `t3 project add <path> --title …` (idempotent apart from an "already exists" exit) [src]. Per-repo behaviour goes in a committed `t3.json`. For both TfC repos set `worktreeSubmodules: "none"`: routelab has 28 submodules (4.5 GB) and d_abm has 3. Use one setup script that symlinks large untracked directories and runs `pnpm install --offline` (hardlinks).
8. **Never run** `t3 up`, `t3 service install`, `t3 update`, `t3 connect` or the in-app "Update" on Nix hosts. Set `limits.updates.mode="off"` and `enableProviderUpdateChecks=false`.

## 1. What T3 Code is

**Product.** T3 Code is "the open-source control plane for coding agents" (MIT, T3 Tools Inc, 62k stars). It drives Claude Code, Codex, OpenCode, Cursor, Grok, Antigravity, Kiro, Pi, Muse, fx and ACP Registry agents from one UI. Each conversation is a *thread*, threads belong to *projects*, and a thread runs in the main checkout ("local") or in its own git worktree.

**Versions (2026-11-17).**

| Channel | Version | Source |
|---|---|---|
| upstream stable | **v0.1.10** (2026-11-17 01:44 UTC; "1924 changes from 360 contributors") | GitHub releases API |
| upstream nightly | `v0.1.10-nightly.20261116.4800` (about 4 nightlies a day) | releases API |
| llm-agents.nix (main and our lock `47a7bbf`) | 0.1.9 | `packages/t3code/unwrapped.nix` [nix] |
| nixpkgs `nixos-unstable` | 0.1.8 | `pkgs/by-name/t3/t3code/unwrapped.nix` [nix] |
| nixpkgs 26.05 | 0.0.24 (per the baseline module's comment; too old) | — |

Pre-1.0 with heavy churn: the 0.1.10 release alone has 1924 changes. Settings and policy keys appear between minor versions. `keepAwakeWhileAgentsWork` and `requireConnectDeviceApproval` exist in 0.1.10, and the 0.1.9 `t3 policy check` **rejects** both [bin].

**Architecture** [src, `docs/internals/overview.md`].

- **Server** (`apps/server`, Node 24/26, Effect-TS). One process per *T3 home*. It owns the SQLite event store, the provider sessions, terminals (node-pty), git and worktree operations, a headless Chromium for agent browser tabs, an MCP server at `/mcp`, and a static web UI. The CLI entry point is `t3`.
- **Web UI.** Served by every server, and also hosted at `app.t3.codes`, which connects *directly* to your server's HTTPS endpoint.
- **Desktop app** (`apps/desktop`, Electron 44). It is a client and can also host its own *local environment* server. It stores saved remote environments with encrypted bearer tokens.
- **Mobile** (iOS "T3 Code Remote", Android `com.t3tools.t3code`). Client only.
- **T3 Connect** (optional). A Clerk-authenticated relay plus Cloudflare tunnels (`cloudflared` 2026.10.4, downloaded unless `T3CODE_CLOUDFLARED_PATH` is set) [src `packages/shared/src/relayClient.ts`]. It provides access without a VPN, mobile push, webhooks and the hosted MCP.
- **Orchestration protocol** version **2** [src `packages/contracts/src/environment.ts:13`]. A client and a server on different protocol versions refuse to connect [doc `updating.md`]. Minor-version skew (for example the store mobile app against a Nix server one release behind) is fine while the protocol stays at 2.

**On-disk state** [src `apps/server/src/config.ts` `deriveServerPaths`]. T3 home is `~/.t3`, overridable with `T3CODE_HOME` or `--base-dir`.

Expect `statev2.sqlite` to grow to GBs. butternut's `/` is **93 % full (126 G free)**, so watch it. `t3 doctor --dry-run` reports what can be reclaimed.

### 2.5 `settings.json` and `keybindings.json` writes: why `mutable*=false` is wrong here [src]

- `writeFileStringAtomically` (`packages/shared/src/atomicWrite.ts`) **resolves symlinks and writes next to the target**. An HM `home.file` symlink into `/nix/store` therefore makes every write fail (EROFS).
- The server writes `settings.json` during **load** whenever a migration changes something (`apps/server/src/serverSettings.ts` `loadSettingsFromDisk`). Triggers include:
  - `foldProviderInstanceEnabledFlags`: a `config.enabled` inside a provider instance. The baseline module and HM's own example both set it.
  - `foldLegacyProjectSettings`: runs once projects exist and `projectSettingsFolded` is false.
  - `moveInlineSettingsSecrets`: a sensitive value written inline.

  A failed write makes "settings.start" log a warning and run degraded. After that, *every* UI change fails.
- The server also writes `keybindings.json` at startup to backfill new defaults (`apps/server/src/keybindings.ts` `syncDefaultKeybindingsOnStartup`). If that fails, the keybindings runtime doesn't start.
- **Therefore:** `mutableUserSettings = true` and `mutableKeybindings = true`. HM then merges the Nix values over the file at every activation (`$dynamic * $static`; keybindings are grouped by `[key, when]`) [nix `modules/programs/t3code.nix`]. Nix wins on each switch, and UI state such as project overrides survives. Anything that must *never* drift goes in the **policy** (locked) instead.

### 2.6 Keybindings [doc `keybindings.md`, src `packages/contracts/src/keybindings.ts`]

Rules have the form `{key, command, when?}`. `mod` = Ctrl on Linux. The last matching rule wins. Context keys: `terminalFocus`, `terminalOpen`, `previewFocus`, `previewOpen`, `rightPanelOpen`, `modelPickerOpen`, `usagePageOpen`, `composerFocus`, `draftThreadRoute`, `turnRunning`, `editableFocus`, `isWeb`, `isDesktop`.

Defaults worth knowing: `mod+shift+m` model, `mod+shift+h` host, `mod+shift+a` permissions, `mod+shift+x` workspace, `mod+shift+g` branch, `mod+shift+l` reuse the previous worktree, `mod+alt+Enter` send to background and open a new composer, `mod+1..9` threads (desktop only), `mod+k` palette, `mod+z` undo sidebar action, `mod+[`/`]` back/forward.

Unbound by default (bind these): `thread.stop`, `thread.regenerateTitle`, *Composer: Cycle Host*, *Increase/Decrease Effort*.

Proposed additions (they live on **each host**, so they belong in the `agent-host` HM config). Command ids for the unnamed ones should be copied from Settings → Keybindings [verify]:

```nix
keybindings = [
  { key = "mod+shift+period"; command = "thread.stop"; when = "!terminalFocus"; }
  { key = "mod+alt+t"; command = "thread.regenerateTitle"; }
  { key = "mod+j"; command = "terminal.toggle"; }
  { key = "mod+shift+d"; command = "diff.toggle"; when = "!terminalFocus"; }   # verify id; default mod+shift+d is dictation
];
```

The browser takes `mod+w` and `mod+shift+t`, so in the web UI rebind `rightPanel.close` and `terminal.close` to `alt+w` [doc]. Sway's modifier is Super and never collides with `mod` = Ctrl.

### 2.7 Client settings (desktop `client-settings.json`, flat object) [src `ClientSettingsSchema` settings.ts:405]

HM **26.05**'s example nests these under `settings = {…}`. Current T3 reads a **flat** object, which is what HM master's example shows [nix]. Use the flat form. Useful keys:

- `sendShortcut`: `enter` | `mod-enter-multiline` | `mod-enter`
- `followUpBehavior`: `queue` | `steer`
- `notificationMode`, `inAppNotificationsEnabled`
- `diffLayout`, `diffIgnoreWhitespace` (default true), `diffFilesCollapsed`
- `sidebarProjectGroupingMode` (`repository` groups the same repo across hosts), `sidebarThreadSortOrder`
- `timestampFormat`
- `loadBalancingEnabled` / `loadBalancingWeights` (§3.5)
- `favorites: [{provider, model}]`
- `fontFamily*` and `fontSize*`: use the theme fonts from `self.theme` if exposed. Never hardcode colours.
- `confirmThreadDelete`
- `toolCallVisibility`

The web UI keeps the same preferences in browser storage, so it can't be configured declaratively.

## 3. Remote access and Tailscale

### 3.1 Options [doc `remote-access.md`, src]

| Option | URL | Encryption | Auth | app.t3.codes / MCP / linked envs / secure-context features | Verdict |
|---|---|---|---|---|---|
| `--host <tailscale IPv4>` (current baseline) | `http://100.x.y.z:3773` | WireGuard only; plain HTTP to the browser | pairing token | **no**: these require HTTPS; MCP "lets an agent find the environment but not finish signing in" | replace |
| **loopback + `--tailscale-serve`** | `https://butternut.<tailnet>.ts.net/` | TLS (Let's Encrypt via Tailscale) + WireGuard | pairing token | **yes** | **recommended** |
| `--lan` / `T3CODE_LAN` | LAN and tailnet IPs over HTTP | — | pairing token | no | skip |
| Tailscale Funnel | public internet | TLS | token only | yes | **no**: needless exposure |
| T3 Connect | `*.t3.codes` tunnel | TLS via cloudflared | Clerk account + device approval | yes, plus **phone push** and webhooks | maybe later. Puts a third party (T3 relay and Clerk) in the trust path; 3 machines free |
| Desktop-managed SSH | port forward | SSH | SSH | n/a | **no**: downloads a non-Nix runtime into `~/.t3/runtime` on the host |

With a loopback bind, the auth policy is `loopback-browser`. Requests arriving through Tailscale Serve come from 127.0.0.1, and the server takes the client IP from the last `X-Forwarded-For` entry [src `apps/server/src/auth/utils.ts:172`]. Every client still needs a pairing token or session. No IP-based trust exists.

### 3.2 One-time prerequisites (imperative, documented)

1. Tailnet admin console: enable **MagicDNS** and **HTTPS certificates**. Certificate names go to public CT logs, which reveals machine names such as `butternut.<tailnet>.ts.net`.
2. Tailscale operator for the service user. T3 runs `tailscale serve` as hfahmi. Declare it with `services.tailscale.extraSetFlags = ["--operator=${user}"];` (agent-host). If the operator is missing, T3 still starts but can't add the HTTPS route, and `t3 pair --tailscale` names the fix [doc, release notes #37466].
3. Tailnet ACL (recommended): allow `tcp:443` to `tag:agent-host` only from your own devices.

### 3.3 Pairing (once per client per host)

Pairing is inherently imperative. Saved environments store a per-server `environmentId` plus a bearer token encrypted with the client's keychain (`apps/desktop/src/settings/DesktopSavedEnvironments.ts`) [src]. Nix can't pre-seed them.

```bash
# from hazel, for each host:
ssh butternut t3 pair --label hazel-desktop --ttl 10m     # prints the https://…ts.net pairing URL and a QR code
# phone: scan the QR from `ssh -t butternut t3 pair --label iphone`
```

Once the server is running with `--tailscale-serve`, `t3 pair` prints the tailnet HTTPS URL. If it doesn't, use `t3 pair --tailscale` [doc].

Use scopes for less-trusted clients, for example a phone that should only read and steer:

```bash
t3 pair --scope orchestration:read --scope orchestration:operate --scope terminal:read --label phone-readonly
```

The full scope list [bin]: orchestration:read/operate, settings:write, providers:manage, environment:maintain, preview:operate, diagnostics:read, terminal:read/operate, filesystem:read/write, source-control:write, access:read/write, relay:read/write.

To manage sessions: `t3 auth session list` and `t3 auth session revoke <id>`. Pairing-issued sessions expired after a hard-coded 30 days until #33183 (closed 2026-11-17, fixed in 0.1.10+ [verify]). **On version < 0.1.10, expect to re-pair monthly.**

### 3.4 One client UI for many hosts

- **Desktop app on hazel (recommended).** Install `llm.t3code.desktop` and pin it to Sway workspace 5 (`app_id`/WM class `t3code`). Switch **Settings → Environments → Local environment** off, because hazel is only a client [doc "Using the Desktop App as a Remote Only"]. Pair butternut, peacelily, maple and the AWS VM as environments. The sidebar groups the same repository across hosts (`sidebarProjectGroupingMode = "repository"`). `mod+shift+h` picks the host for a new thread, and *Cycle Host* steps through hosts.
- **app.t3.codes** in any browser works against HTTPS endpoints. Its saved environments live in that browser's storage, and the hosted app always runs the latest version (protocol v2 skew risk, §1).
- Each server's own web UI at `https://<host>.ts.net/` is the zero-install fallback. Saving *other* hosts there is unverified (CORS) [verify].
- **Routes:** one machine can have Tailscale HTTPS plus learned LAN and Tailscale addresses. T3 tries routes in order and falls back, checking every minute [doc]. With HTTPS-only pairing you get one route per host, which is enough.
- **The `target <need>` resolver** stays outside T3. It answers "where should this work run?", and you then choose that host with `mod+shift+h`. T3's optional **Auto balance** (client setting `loadBalancingEnabled`, weights Prefer/Normal/Less often/Manual only) picks a machine for new threads in projects grouped across environments, by CPU and RAM [doc]. Turn it **off**. Our targets differ by *capability* (Android emulator, GPU, data present), not load, so the resolver should decide.
- **Linked environments (beta, Labs).** Agents on one host can `delegate_task` to another host's project with the same repository. Links last 30 days and need a pairing code; HTTP is refused (#26840), so HTTPS is required. This is the native way for an orchestrator thread on butternut to farm out a run to peacelily. Useful later.

### 3.5 Security implications

- Anyone holding a full-scope token, **and any full-access agent or terminal on the host**, can manage access: mint pairings, read `~/.t3`, run `t3 pair`. This is inherent [doc]. Treat agent hosts as fully trusted by their agents, and keep personal secrets (rbw, GPG, email) off the agent hosts or out of the agent user's reach.
- T3 Connect off (`limits.connect=false`) removes the third-party relay. `limits.webhookTasks=false` and `browserCookieImport=false` close the other inbound and outbound paths.
- `t3 pair` links are bearer secrets. Default TTL is 5 minutes, and they are single-use [doc][bin].
- Tailscale Serve config persists in tailscaled state. If T3 is removed, run `tailscale serve --https=443 --set-path=/ off` [doc].

### 4.4 Pointing at Nix binaries robustly

| Approach | On a CLI bump | On a T3 bump | Verdict |
|---|---|---|---|
| T3 wrapper's own `PATH` prefix (nixpkgs `enableClaude` / llm-agents `providerPackages`) | T3 restarts, since the closure changed | — | heavy closure (2.2 GiB extra), and a *second* Claude CLI that ignores our HM `claude` wrapper (plugins, MCP) |
| Store path in the policy `binaryPath` (`${claude}/bin/claude`) | policy changes → the unit must restart to apply | — | exact, but every bump interrupts agents |
| **Stable profile path `/etc/profiles/per-user/hfahmi/bin/claude` in the policy (locked)** | new sessions use the new CLI; running sessions keep the old process | unaffected | **recommended**. Requires HM `useUserPackages = true` (already set in `modules/nixos/extra/hjem/hjem.nix`) |

Policy fragment (validated with `t3 policy check` on 0.1.9 [bin]):

```json
"providers": {

  "instances": {
    "claudeAgent": { "locked": true, "binaryPath": "/etc/profiles/per-user/hfahmi/bin/claude" },
    "opencode":    { "locked": true, "binaryPath": "/etc/profiles/per-user/hfahmi/bin/opencode" }
  }

```

**Do not set `limits.maxRuntimeMode`.** Setting it hands *all* provider launch settings (env vars, launch args, config home) to the policy, so the UI can no longer change them [doc].

## 5. Projects and worktrees

### 5.1 Project discovery and registration

Projects are rows in `statev2.sqlite`: an id, a title and a workspace root. They are added in the UI (Add project, folder search, clone from GitHub with optional ghq layout via `addProjectBaseDirectory` and `ghqCloneLayout`), with `t3 app <path>` (desktop only), or with **`t3 project add <path> [--title X]`**. The CLI form works against the running server ("live" mode via a local session token) or offline [src `apps/server/src/cli/project.ts`]. Re-adding an archived project unarchives it, and an existing active project returns `ProjectAlreadyExistsError` (non-zero exit), so a "register if missing" loop is safe.

Declarative registration, per host (§6.3): `preferences.agents.t3code.projects = [ { path = "/home/hfahmi/work/tfc/repos/routelab-monorepo"; title = "RouteLab"; } … ]` drives a `t3code-projects` user oneshot that runs after `t3code.service`. List only checkouts that exist on that host. A project present on several hosts appears grouped by repository in the client.

**OpenCode** has no project registry to seed. It keys sessions by the git repository it runs in (from OpenCode's design; [verify] against the current `opencode` docs).

### 5.2 Worktree mechanics [doc `project-settings.md`, src]

- Location: `worktreesDirectory`, or `~/.t3/worktrees/…`. Keep it on the same filesystem as the main checkouts and the pnpm store (hardlinks). On butternut everything is on ext4 `/`, which has no reflinks. The macOS-only "fast worktree checkout" cache is irrelevant here.
- Creation: branch from origin (`newWorktreesStartFromOrigin`), initialise submodules according to `worktreeSubmodules`, then run the setup script (`async: true` by default, meaning the agent starts in parallel). New worktrees refresh their index once (0.1.10 #21341).
- Branch names: static `t3/…`, semantic, or custom instructions. Directory names don't change when the branch is renamed.
- **Cleanup** (off by default; runs at startup, hourly and on change). Rules:
  - inactive days
  - settled-thread days (0 = at the next cleanup)
  - on merge (PR merged into the remote default branch; squash and rebase count)
  - unchanged (no commits beyond default)
  - on thread delete

  "Keep when" options:
  - `uncommitted-changes` (default) keeps tracked edits and untracked files, but **deletes ignored files**
  - `any-local-files` keeps everything except `node_modules`
  - `tracked-changes`

  Only T3-managed worktrees are touched. Folders nobody uses are only *listed*.
- **[verify before trusting cleanup with symlinks]:** cleanup must remove our symlinks without following them into the 60 GB `d_abm/output`. Node's `fs.rm({recursive})` and `git worktree remove` don't follow symlinks, but test it once on a throwaway worktree with a symlink to a sacrificial directory.

### 5.3 Getting the devShell into agents (T3 has no direnv support)

The server inherits only the login-shell PATH, so `claude` runs in the worktree **without** the project devShell. Three layers, use all of them:

1. **Setup script:** `direnv allow` the new worktree path. direnv's allow list is per path, and every worktree is a new path. Then warm the shell with `direnv exec . true`, so nix-direnv builds and GC-roots `.direnv/` once.
2. **Claude `SessionStart` hook (global, in nixconf `programs.claude-code`):** when `.envrc` exists and is allowed, run `direnv export bash >> "$CLAUDE_ENV_FILE"`. Claude Code then sources it before each Bash tool call, so the agent gets the devShell for every command [verify `CLAUDE_ENV_FILE` semantics in the current Claude Code docs]. This needs no wrapper and no T3 support.
3. **AGENTS.md rule** as the fallback: "Run project tools via `direnv exec . <cmd>` if a command is missing."

T3's integrated terminals run your interactive fish, so its direnv hook works there as it does anywhere.

Alternative to (2): a per-project `binaryPath` wrapper that runs `direnv exec "$PWD" claude "$@"`. Rejected: binaryPath is per instance (machine-wide), the wrapper would slow every session start, and the policy locks binaryPath.

**Slices:**

- T3 spawns provider sessions and terminals with `systemd-run --user --scope --slice=app-t3code-agents-<hash>.slice` (`--property=Delegate=yes`, `OOMPolicy=stop` where supported). At each launch it sets runtime properties: `MemoryHigh=max(total−6 GiB, total/2)` and `MemoryMax=max(total−4 GiB, 0.75·total)` on the agents slice, and `CPUWeight=10 IOWeight=10 TasksMax=25%` on `app-t3code.slice` [src `apps/server/src/process/agentScope.ts`]. Our persistent `MemoryMax/High` on the parent `app-t3code.slice` still caps the whole subtree, and the runtime `CPUWeight` overrides ours (fine).
- Requirements: `systemd-run` and `systemctl` on the server's PATH (`/run/current-system/sw/bin`) and `XDG_RUNTIME_DIR` set (it is in user services).
- herdr and `agent-run`: move them under the same budget with `Slice=app-t3code-manual.slice` (a child of `app-t3code.slice`), or keep `agents.slice` as a second, separate cap. A shared parent gives *one* budget for all agent work. T3's `stopLeftoverAgents` stops only its own hashed slice [src].
- Check with `systemd-cgls --user-unit app-t3code.slice` and `grep app-t3code /proc/<claude-pid>/cgroup`.

**Logs:** `journalctl --user -u t3code` (stdout/stderr) plus `~/.t3/userdata/logs/server.trace.ndjson` (rotating, 10 MiB) and `logs/provider/events.log`. `t3 trace` inspects the trace.

### 6.4 Secrets

- Nothing in settings, keybindings or the policy is secret. `/etc/t3code/policy.json` is world-readable by design [doc]. The repo stays public-safe.
- Optional `EnvironmentFile` through sops-nix (`secrets/<host>/t3code.env`, owner = user, mode 0400). Use it for `GH_TOKEN` if you don't run `gh auth login` on the host, and for `OPENCODE_SERVER_PASSWORD` if OpenCode is pointed at a shared server. Provider API keys belong in each CLI's own config (Claude subscription login, OpenCode auth), not in T3.
- The provider instance `environment[]` with `sensitive=true` moves values into `~/.t3/userdata/secrets/` on first load and redacts settings.json [src]. Don't put such values in Nix.

The baseline module's `xdg.desktopEntries.t3code-remote` (opens `http://<target>:3773`) becomes a fallback pointing at `https://<target>.<tailnet>.ts.net/`.

### 6.6 How updates flow

1. Bump `llm-agents` in `flake.lock`. CI builds it, and the binary cache serves it, so hosts only download.
2. The build runs `t3 policy check` against the new version. A removed or renamed key fails the build, not the service.
3. `nixos-rebuild switch`, then `sd-switch` restarts `t3code.service`, because the ExecStart store path changed. With `continueThreadsAfterServerUpdate` (default on), supported active threads resume. Terminals and dev servers are interrupted. Threads waiting for approval don't resume [doc]. **Switch when no turn is mid-flight**, or accept the interruption.
4. The database migrates forward on start. **Rolling back** to an older generation can hit "database has changes the target release does not support" [doc `updating.md`]. Snapshot `~/.t3/userdata` (or the btrfs/ZFS dataset) before bumps across minor versions.
5. Clients: the hazel desktop comes from the same flake. The phone app updates from the store; keep hosts within a release or two.
6. Never let T3 self-update. Policy `updates.mode = "off"` disables the checks. `respawn` / `boot-service` self-update methods would write non-Nix runtimes into `~/.t3/runtime` [src `ServerSelfUpdateMethod`].

### 6.7 Corrections to the baseline `modules/nixos/features/agent-t3code.nix`

| Baseline | Change | Why |
|---|---|---|
| `mutableUserSettings = false` | `true` | §2.5: write failures |
| `config.enabled = true` inside each provider instance | drop it; keep the instance-level `enabled` | migration rewrite on load |
| `--host <tailscale IPv4>` + HTTP URL | `--host 127.0.0.1 --tailscale-serve` + operator flag | HTTPS for app.t3.codes, MCP, linked envs, voice |
| `Slice = "agents.slice"` | no Slice on the server; cap `app-t3code.slice` | T3 moves agents into its own slices anyway; the server needs protection |
| `llm.t3code` | `.override { providerPackages = []; }` | −2.2 GiB closure, no duplicate CLIs |
| binaryPath in `userSettings` | in `/etc/t3code/policy.json` (locked) | can't drift through the UI |
| — | policy: `updates.mode=off`, `telemetry=false`, `connect=false`, text generation on Claude | §2.3 / §3 |
| — | `t3code-projects` oneshot | declarative projects |
| `Restart=on-failure` | `always`, plus T3's KillMode/OOM properties | matches upstream's unit |

## 7. Workflow

### 7.1 Start a stream

1. `target heavy` returns, for example, peacelily.
2. In the T3 desktop (workspace 5), use *New thread* (`chat.new`, or `mod+k` → New thread), pick the project, press `mod+shift+h` and choose the target host. Workspace = **New worktree** (the default via policy).
3. Pick the model (`mod+shift+m`) and mode (`mod+shift+a`). For long autonomous tasks use Full access in a worktree. Then write the prompt. `mod+alt+Enter` sends it, keeps it running in the background and opens a fresh composer for the next stream.
4. The setup script runs (symlinks, `direnv allow`, `pnpm install --offline`) before the agent starts (`async:false`).

### 7.2 Review and land

- **Diff panel**: scopes are working tree, branch vs base, per turn [verify scope names]. `mod+f` searches the diff, and line comments go back to the agent as feedback.
- Rewind and restore: per-turn checkpoints (server `checkpointing/`) [verify UI]. Native resume of stopped Claude and OpenCode threads arrived in 0.1.10.
- **Source control**: commit (the commit message comes from the text-generation model), push, open a PR via `gh` (diff, checks, review guides, merge from the PR panel). Agents "watching pull requests" resume when checks pass. Merge settles the thread (`sidebarAutoSettleOnMerge`), and cleanup removes the worktree after the merge.
- Heavy review stays in lazygit or difftastic over `ssh`/`herdr --remote` when wanted. The worktree path is shown in the thread.

### 7.3 Switching targets mid-stream

Have the agent commit and push, then start a new thread on the other host on the same branch (`mod+shift+g` → the branch). Threads don't migrate between hosts. Linked environments (§3.4) can `delegate_task` instead.

### 7.4 Notifications

- **Primary: Claude Code hooks** (`Stop`, `Notification`) → ntfy → swaync on hazel and the phone, as designed. **Verify they fire for T3-driven sessions** (§4.1). If `Notification` doesn't fire for SDK permission prompts, T3's own UI shows the pending approval: desktop notifications come from the client's `notificationMode` setting.
- Phone push from T3 itself requires T3 Connect plus "Publish agent activity" (it sends titles and status to T3's relay) [doc `mobile-notifications.md`]. It is not available with `connect=false`. ntfy covers this.
- Scheduled tasks (cron or once) exist per environment. **Webhook tasks need a T3 Connect URL** (disabled here).

### 7.5 Phone check-ins

Install the T3 Code mobile app and the Tailscale app, then pair each host over its `https://…ts.net` URL (QR from `ssh -t host t3 pair --label phone`). The phone can read, steer, approve, answer questions and watch the agent's browser or device streams. **Avoid opening device or browser video over mobile data.**

Known issue: an iOS app retrying an offline Tailscale environment could freeze the tunnel (#37699, closed 2026-11-16). Remove AWS from the phone while that VM is stopped.

### 7.6 Orchestrators, herdr and T3

- T3 runs Claude through the SDK, so herdr doesn't see those sessions. Use **T3 for streams** and **herdr for raw CLI agents** (long manual sessions, TUIs).
- An orchestrator agent can drive T3 instead of nesting subagents:
  - `t3 thread start|send|show|list` on the host [bin]
  - or the T3 **MCP server** at `https://<host>.ts.net/mcp` (outside agents; sign-in needs HTTPS or localhost [doc `outside-agents.md`])

  Each worker becomes a normal thread in the inbox with its own worktree, which fixes the "interleaved subagent transcript" problem.
- T3 threads can also delegate natively (`delegate_task`, subagent hover cards).

### 7.7 Bandwidth checklist (Egypt)

| Setting | Value | Effect |
|---|---|---|
| `worktreeSubmodules` | `none` | no submodule clones per worktree |
| `automaticGitFetchInterval` | 5 min | fewer background fetches |
| `enableProviderUpdateChecks` | false | no catalog downloads |
| `providerPackages` | `[]` | −2.2 GiB per T3 bump |
| `responseStreamingMode` | `paragraph` | — |

Also: pnpm `--offline`; no Funnel or Connect; browser and device streams only on demand; CI plus the binary cache for all store paths.

## 8. Gaps, risks, first-run checklist

**Risks:**

- **Pre-1.0 churn.** About 4 nightlies a day, and policy and settings keys change between minors. The build-time `t3 policy check` turns that into build failures. Keep the policy minimal.
- **Packaging lag.** llm-agents 0.1.9 against upstream 0.1.10. The mobile and hosted clients run the latest version, which is safe while orchestration protocol = 2.
- **Database growth and write amplification** (#37600, #37877) on a 93 %-full disk. Monitor `~/.t3/userdata`, and run `t3 doctor --dry-run` monthly.
- **Things the server writes itself:** settings and keybindings (handled by staying mutable), the Tailscale Serve config (persists in tailscaled), the browser download (~120 MB headless Chrome into T3 home: a non-Nix binary). There is `T3CODE_…` support for a system-managed browser (#31740, open) [verify a Nix chromium path option once merged].
- **No direnv integration.** Covered by setup scripts, the Claude SessionStart hook and AGENTS.md (§5.3).
- **Linux specifics:** no fast worktree checkout (macOS only). The headless Chrome sandbox may need `T3CODE_SERVER_BROWSER_SANDBOX=0` if Chromium can't start its sandbox on NixOS [verify]. The Android Device panel needs `ffmpeg` with libx264 and `ANDROID_HOME`.
- **Pairing is imperative and per client.** Sessions expired after 30 days before 0.1.10.
- **T3 Connect off** means no phone push, webhooks or hosted MCP. That is a deliberate tradeoff.
- **Terminal and full-access agents can mint T3 access** (§3.5).

**First run, per host:**

1. `t3 policy show`: the policy is loaded and the fingerprint matches. Settings show "Managed by nixconf".
2. `systemctl --user status t3code`, then `curl -sI https://$(hostname).<tailnet>.ts.net/` returns 200 over the tailnet. `tailscale serve status` shows `/ → http://127.0.0.1:3773`.
3. `claude auth login` (and `opencode auth login`) on the host. Settings → Providers: Claude is ready, OpenCode is ready, the versions aren't flagged, and Codex isn't listed.
4. Start a throwaway thread in a worktree. Check that `grep app-t3code /proc/$(pgrep -n claude)/cgroup` matches, that `~/.t3/userdata/settings.json` is a regular writable file, and that changing a setting in the UI persists across a restart.
5. Check that the Claude `Stop` hook reaches ntfy for a T3 thread.
6. Check that the setup script ran: the symlinks exist, `direnv status` shows allowed, and `pnpm install --offline` succeeded without network.
7. Worktree cleanup dry test with a symlink to a sacrificial directory (§5.2), *before* enabling the cleanup rules.
8. `t3 project add` oneshot: both TfC projects appear with titles, on this host only if checked out.
9. Pair hazel and the phone, then disable *Local environment* on the hazel desktop.

**Open questions for the user:**

- d_abm outputs: shared symlink plus per-worktree `output_root` (proposed), or fully separate?
- Commit `.envrc` in d_abm (recommended)?
- Enable T3 Connect later for phone push (third-party relay)?
- Default permission mode: `auto-accept-edits` (proposed) or Full access in worktrees?
